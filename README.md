# layout-viewer

一个基于 KLayout 实现的版图（GDS/OAS）查看工具。

## 插件化架构

【**Situation**】 本工具的功能模块（ruler、select、goto等）都需要与主窗口、资源树、画布交互。以 ruler 为例：常规做法是在画布的鼠标事件处理里直接创建 ruler 对象并绘制，由此带来两个问题：
- 画布只负责显示和处理鼠标事件，却承担了创建、管理 ruler 的职责——违背单一职责原则
- 若新增功能模块需要与画布交互，都要在鼠标事件处理流程里增加条件分支；且画布会直接依赖该功能模块的具体实现而非抽象接口——违背开闭原则与依赖倒置原则

随着功能模块增多，耦合度不断上升，代码维护成本也随之增加。

【**Task**】 基于上述情况引入插件化架构，把功能模块从主程序中剥离，使主程序只依赖插件的抽象接口，做到新增或移除功能时不改动主流程。

【**Action**】 以 ruler 为例，功能以插件形式接入；主程序只依赖三个抽象接口：插件声明接口（负责声明与创建插件实例）、插件接口（负责行为、菜单与配置）、视图服务接口（负责视图内的事件处理）。
- **插件注册**：各插件的声明对象由文件作用域的静态注册器在程序启动前完成登记，并按注册时指定的优先级排序；注册器持有声明对象的生命周期，进程退出时注销并释放。增删插件只需增删对应源文件，主流程零改动。
- **主界面装配**：主窗口初始化时遍历注册中心，收集各插件声明的菜单项、工具栏动作与配置页，统一装配菜单、工具栏与"设置"对话框；主程序代码中不出现任何具体插件类型。
- **画布交互**：布局视图初始化时遍历注册中心，为每个插件创建实例；插件自建视图服务并注册到视图控件。鼠标事件由控件统一分发：先交给已抢占鼠标的服务（后抢占者优先），再交给活动服务，最后按序询问其余服务，任一服务确认已处理即消费该事件、不再向下传递；画布既不创建、也不认识任何具体插件。
- **资源树同步**：创建插件时注入资源树，标尺数据变化时插件把最新列表同步给树，由树刷新对应条目。

【**Result**】 新增一种工具只需新增"插件声明 + 插件实现 + 视图服务 + 配置页"等组件，主程序与既有插件零改动；从构建中移除该插件后，其菜单、工具栏、配置页与全部代码都不会进入产物。
